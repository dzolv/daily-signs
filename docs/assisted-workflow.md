# 她选图，模型接手制作

目标是保留逛图、挑图和决定构图的乐趣，把重复排版、替换文案、导出、压缩和整理交给模型。日常路径和实验路径共用同一份本地制作记录，随时可以换回自己选图。

## 日常路径

她照常在 Figma 或 Pixso 里挑图、放图、调整构图。第一次使用时，和模型确认哪个现有画板、页面或选区表示本次工作，以及哪些部分只是参考。优先沿用她已有的命名和摆放习惯；只有现有结构无法区分时，再约定一个待制作区域。

之后可以直接说：

> 这次的图已经放好了，读取上次的日签区域，按这次参考和最新反馈接着做。

模型从已经授权的设计工具读取图层、文案、图片和当前构图，保存本地快照。她不用重讲文案、重新下载并上传图片，也不用为程序填 JSON。CLI 的输入文件由模型根据工具返回的真实数据准备。

画板中存在一张图，只说明它在画板中。只有之前约定的区域、明确的标记或她的明确选择，才能把它认定为本次选图。参考图、候选图和已选图必须分开记录。

## 实验路径：按她的习惯提供一组方案

她可以说：

> 参考我以前选过的图和这次的文案，给我几种找图方向。我想自己挑，选好后再接着制作。

模型先读取她指定的历史成品或参考区域，形成有出处的观察，例如某几期偏好自然光、某个模板需要文字区留白。每条观察都应指向具体例图或反馈，并标明是她确认过的习惯，还是模型暂时推测。不能因为她选过一次，就把某种风格写成永久偏好；未经选择的图也不等于她不喜欢。

第一轮可以提供三种不同程度的探索：

| 方案 | 怎样参考她的习惯 | 给她看的内容 |
| --- | --- | --- |
| 沿用熟悉的风格 | 复用已确认的色调、主体或构图偏好 | 适合本次文案的候选与推荐原因 |
| 小幅变化 | 保留熟悉的部分，只改变一个维度 | 哪一点延续原习惯，哪一点有变化 |
| 自由探索 | 围绕主题探索新的方向 | 为什么值得逛，不预先认定她会喜欢 |

这只是起始组织方式，她可以直接调整。每组都应有实际可查看的图片或图库入口、出处与授权状态、适配模板的说明；不要只交付抽象风格词。候选数量按她的浏览习惯控制，不强制她完成打分表或固定筛选轮次。

模型按“本次主题 → 少量中英文检索词 → 可用来源 → 看实际图片 → 看模板内的裁剪”找图。可用 API 批量取得候选，浏览器补充发现与核对。程序保存候选和选图结果，模型的推荐不会自动变成最终选图。

当前优先像人一样通过 Browser 插件浏览、看图和挑参考；不需要先建设搜索系统。灵感阶段保留出处，版权未知可继续展示和讨论，不阻塞候选；准备正式使用时再核实授权或寻找可用替代。参考图不自动成为正式选图。

### 素材来源

- [Openverse API](https://docs.openverse.org/api/) 可按授权检索并返回作品原始页面；用作候选发现入口。需要回到原始页面核对授权，聚合结果不等于授权保证。
- Pinterest 等灵感平台可用于理解风格或发现作品。不能因图片可见、可下载，就认定可商用或为 CC0。
- 明确区分 CC0、其他允许商用的许可和授权未知。需要署名时保留署名要求；只有她接受的授权条件才能用于最终交付。
- [CC0](https://creativecommons.org/publicdomain/zero/1.0/) 不自动解决人物肖像、商标等其他权利问题。记录事实，不由模型宣称“绝对无版权风险”。

自己选入设计文件的图片也可能没有来源信息。先读取并保存，缺失的授权信息记为未知；不能要求她重新描述图片内容，也不能从画板截图反推出授权。

## 模型与程序各自负责什么

模型负责理解习惯、找图、解释方案、调用设计工具以及检查视觉结果。程序负责保存事实、核对版本、分配执行权、保存步骤和验证交付文件。

机械步骤优先使用 [workflow 薄 CLI](../tools/workflow/README.md)。`preflight` 聚合离线 setup/依赖与指定许可，维护到期不打断制作；`save-export` 接收宿主完整 MCP 返回，自动解码、压缩并保存事实回执，不手抄 Base64 或逐轮重写验证脚本。CLI 没有 MCP 连接，返回数据仍由宿主完整转存。`snapshot` 保存真实节点观察，`compare --allow` 断言只有指定属性变化，保护圆角、裁剪、蒙版与构图。试排和接续也能记录，无须伪造正式选图/许可；机器检查不证明未观察属性、来源真实性或审美质量。

正常制作少旁白，把交接尽量留给程序；模型仍直接使用 Pixso 完成读取、设计和导出。优先本次新参考与最新反馈，无须固定模板。视觉快速看清文字、无明显漏字即可，不反复精修已接受的画面。`batch-export` 根据显式清单处理指定 PNG，默认保原尺寸；`resume-batch` 从本地 report.json 校验并恢复，避免新聊天重压成功项或猜最新版。清单可附本次参考、brief 和目标定位；它只是本地批压交接，云端仍需重新读取和模型判断。

复用本仓库现有 Node.js 环境和 PNG 压缩器。交接 CLI 使用本地 JSON、原子替换和写入锁，不增加数据库、后台服务或专用界面；这里只需要一个小批次的本地交接，不需要通用任务平台。

运行 `npm run handoff -- --help` 查看命令。准确输入格式、状态约束和可运行示例见 [交接 CLI](../tools/handoff/README.md)。她不需要亲自运行这些命令。

新会话按以下顺序工作：

1. 读取仓库规则和该批次的交接记录，知道素材、已选方案、完成步骤与下一步。
2. 检查自己能否访问相同设计文件及所需工具。重新读取目标区域，更新快照；不继承另一个聊天的临时选区、浏览器标签或登录状态假设。
3. 按记录认领制作任务。同一批次只允许一个执行者；同一个设计文件或电脑界面也必须由主聊天协调，避免不同批次同时操作。
4. 每个有外部效果的步骤完成后，记录具体画板、导出文件与检查结果。调用失败或结果不确定时先读取外部状态，避免重试时重复建画板。
5. 交付前重新核对目标输入区域，确认选图与文案没有变化。压缩后运行程序检查，再记录视觉检查结果和待确认项。
6. 主聊天读取结果并展示给她。新会话可以继续使用同一批次，省去重新交接。

每次修改本地记录都带上刚读到的版本号。旧会话如果拿着过期记录继续写入，程序会拒绝；重新读取后才能判断下一步。相同快照重复导入不会重复开工；输入实质变化时，旧选择和执行资格会失效，旧结果保留供追溯。

本地锁只约束遵守 CLI 的执行者，不能锁住她的设计软件，也不能检测未重新读取的云端变化。第一次固定输入区域和制作输出区域时应分开：模型新增的成品不应被误读成她更换了输入。不要把整个设计文件的无关变化当作本次选图变更。

## 从 Figma / Pixso 读取

优先复用官方 MCP，通过当前宿主已经提供的工具取得事实，再由模型调用 CLI 保存。第一版 CLI 接收规范化读取结果，**不内置 Figma/Pixso 连接器，也不会自行扫描账号或监听设计文件**。没有连接时应报告具体缺口，不把示例数据当成真实读取。

当前先实施 Pixso。首次提醒、按工具授权和故障分层见 [Pixso 最小权限](pixso-permissions.md)。模型读取 `setup` 提醒状态，说明后才记录；每个执行会话仍须实际检查工具和目标，说明记录不授予权限。

实际许可由 `npm run consent` 单独保存：先明确账号、文件/区域、操作和工具范围，询问并记录真实答复。已明确同意的同一范围不重复问；每个远端步骤和新执行者通过 `check` 核对范围，新增范围再请求。许可 ID 放进批次进度；本地范围检查不代替宿主审批，也不强制拦截远端工具。

| 来源 | 官方能力与接入注意事项 |
| --- | --- |
| Figma | 可读取图层结构、设计上下文和截图；远程工具还提供素材下载、编辑和上传等能力。桌面 MCP 可以围绕当前选区工作，远程 MCP 需要定位到文件/图层。先保存目标范围，以后复用。 |
| Pixso | 本地与远程 MCP 提供结构读取、节点查询、截图、资源导出及设计编辑等能力。远程使用图层定位；本地通常需要客户端与目标文件保持活动。使用条件包括账号席位、查看权限及修改时的编辑权限。 |

截至 2026-11-06，早期验收已真实完成网页创建可编辑样张、2x PNG 导出和压缩；MCP 已读取测试画板、修改并恢复字号、完整保存 2x PNG 并解码压缩。随后新桌面 Terra 会话已实际接续制作三张，验证创建/替换图层、长短文案和原尺寸 1x PNG 导出；版权未知素材仅用于试排，未标为正式授权交付。真实图库授权核查仍未验收，Figma 尚未接入。工具名称和可用性以当前宿主实际清单为准；历史 2x 成功不代表日常仍要求 2x。

读取时至少保留：

- 目标设计文件和区域的稳定标识，以及本次读取时间。
- 真实读取的文案、模板限制、尺寸、裁剪和布局信息；读取不完整时明确列出缺项。
- 素材在画板中的角色，以及原始图片、渲染导出、截图三者的区别。
- 原作品页、授权依据或“未知”。设计文件位置与作品授权来源是两回事。
- 本地素材与快照的内容指纹，避免短期下载链接过期后无法交接。

截图可以辅助理解构图，不能默认替代高清原图。Figma 的素材下载工具区分导出渲染与原始图片；Pixso 的资源导出不能未经核实就标记为原始上传文件。临时链接可用时及时下载本次需要的素材到 `.local/`，保持原有裁剪关系。

## 模型分工与接续

推荐用 Astra 梳理需求和处理有歧义的选择，6.1 Sol 开发维护工具，6.1 Terra 执行明确的视觉和设计操作。模型名称是可调整的执行偏好，不写死在任务状态机中；缺少某个模型时报告并使用用户同意的替代方式。

桌面主聊天可以在用户明确要求新建制作聊天后，指定可用模型创建执行聊天，并通过任务状态工具跟进。执行聊天不是隐藏的子 Agent，会出现在侧栏。授权跟进后可继续该聊天，无需每个步骤新建一个。

2026-11-06 在桌面 26.1103.31037 实测：直接新建聊天时指定 Terra 仍被型号校验拒绝；向已有 Codex 聊天发送任务并指定 `gpt-6.1-terra` / `high` 成功，实际执行记录确认型号。同一轮通过 Browser 插件打开 Unsplash、点击搜索结果、查看作品截图成功。该轮先导航到执行聊天并显式提及 Browser 插件；尚未单独证明这两项哪个解决了此前浏览器清单为空的问题，因此作为已验证操作顺序复用，不声称是根因修复。具体作品与执行记录留在 `.local/terra-browser-acceptance.json`。

调用浏览器前先检查实际入口；导航超时后先读取标签页真实状态，避免重复开页。只看到插件安装或模型自称不是验收证据：需要实际型号记录和同一轮真实浏览器调用。

CLI 执行也是备选：`codex exec --model` 可以指定模型，读取本地交接记录后执行。启动方式与保存记录分离：本仓库交接 CLI 不自行启动模型，不替用户授予工具访问权限，也不依赖桌面专属的聊天管理工具。

CLI 0.167.0-alpha.3.2 的 Browser 插件已安装启用，但本机新启动的 CLI 会话仍被桌面浏览器访问检查拒绝；这条路线尚未跑通。当前找图采用上述桌面聊天路线，不把它描述成 CLI 浏览器已修复。

新执行者必须先确认工具可用；能选择模型不代表能继承主聊天的浏览器、MCP 或账号会话。电脑操作串行执行，纯读取与独立检查才适合并行。程序记录的是已发生的事实；不能因为执行者说“完成”就跳过文件检查。

参考：[Codex 非交互执行](https://learn.chatgpt.com/docs/non-interactive-mode)。

## 交付与本地边界

默认保留原尺寸 1x PNG，使用显式清单 `workflow batch-export` 复用现有压缩核心，生成每张不超过 204,800 字节的指定 PNG。不扫描整个原始目录，不猜最新版；无法在原尺寸达标则报告。程序检查存在、可解码、尺寸、大小和 hash，模型只需简短确认文字可读、无明显漏字。用户拿 PNG，机器清单/回执留 `.local/`；不再增加严格审美验收。

所有真实素材、设计文件标识、候选、习惯证据、制作状态和成品保存在 Git 忽略的 `.local/`。公共仓库只保留代码、说明和合成示例。密钥和令牌只留在客户端或系统凭据配置中，不进入制作单。

“本地运行”指交接程序和文件落在本机。模型服务、远程 MCP 和 Figma/Pixso 仍可能处理相应内容，不能宣称整条流程离线或数据绝不离开电脑。

第一轮验证用一批真实日签，关注她是否能继续自然地选图、是否无需复述、换会话能否接上，以及选图变化能否阻止旧任务交付。她选图用了多久不是优化目标；反复确认和机械调整减少多少才是。
