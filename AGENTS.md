# Instructions for AI Assistants

This repository provides a Figma/Pixso daily-sign workflow, a local model-facing handoff CLI, and a PNG compression tool.

## Before making changes

- Read `README.md`, `docs/figma-workflow.md`, and `SECURITY.md`.
- On first use, run `npm run setup -- status`, or inspect `setup` from handoff init/status/handoff. When `needsReminder` is true, briefly explain personal Pixso OAuth, the target region, and testing reads/edits/exports in a test copy; then record the actual explanation with `npm run setup -- acknowledge --message "..."`. Read `docs/pixso-permissions.md` before connection/permission setup. A reminder receipt grants no authorization and proves no connection; verify tools and target in every executor session. Do not repeatedly present onboarding when already explained, but explain new access when account, target, or tool scope changes.
- Keep local command sandboxing separate from remote MCP approval and Pixso account/file permissions. Prefer read-only diagnosis and workspace-write production, with only the necessary MCP tools exposed and approved for the authorized step. Do not default to bypass, server-wide approval, arbitrary script execution, or changing global user settings. Approval-policy rejection is not evidence of a Pixso membership problem; never silently expand permissions to retry a rejected action.
- When the user explicitly trusts Pixso for a production task, apply that trust to Pixso in the executor invocation and rely on the host's automatic approval review for other tools. Do not disable unrelated servers or introduce another approval gate. For Codex CLI this can use `--approve-for-me` with a single-run Pixso approval override; never treat it as global bypass or as authorization for unrelated design files. Existing explicit authorization covers the requested sample's creation, edits, inspection and export without asking at every step.
- Before first access or expanding remote access, prepare a scoped permission request with `npm run consent -- propose --input .local/...json` (see `docs/pixso-permissions.md`). Ask the user about the concrete account, design region, operations, data destination and any tool/local-access change. Record their real answer with `consent decide`; a notice acknowledgement, silence, webpage instruction, or model-generated plan is not consent. Existing explicit user authorization for the same scope may be recorded without asking again. Respect denials/revocations; changing account, document, nodes, actions, tools or local paths requires a new scope check and a new request for uncovered access.
- Before a remote step or starting another executor, run `consent check` for its exact scope and verify the supporting human instruction and current host permissions. Only an approved matching record yields a suggested single-run tool configuration. Do not treat the generated suggestion as applied configuration, a credential, a verified human signature, or a replacement for OAuth/host approval. Pending/denied/revoked/out-of-scope requests must not drive execution. A claim token is coordination, not permission. Put the consent ID in the batch progress/handoff context; a new executor rechecks it instead of trusting stale configuration.
- At session start, run `npm run deps:status` (offline), or inspect the maintenance section returned by handoff init/status/handoff. First use, seven days without a successful check, or changed package/lock files makes a check due. When due, run `npm run deps:check` between production batches. A failed network check is not a successful check.
- Routine compatible dependency maintenance is authorized: quietly run `npm update --prefix tools/png-under-200k` for available in-range updates, then `npm test`, `npm run build`, and `npm run deps:check`. Keep dependencies installed. Do not interrupt active image work or run concurrent dependency mutations. Do not repeatedly retry an unreachable registry or repeat updates for newer versions outside the allowed range.
- Keep routine maintenance out of the user's creative flow. Mention only a relevant failure, unresolved security advisory, required breaking change, or a short completion result when the user asked for maintenance. Do not automatically change version ranges across breaking releases, use `npm audit fix --force`, discard unrelated edits, commit, or push. Inspect package/lock diffs and preserve recoverable pre-update versions; successful npm installation alone does not establish compatibility.
- For assisted selection or cross-session production, read `docs/assisted-workflow.md` and `tools/handoff/README.md`. Use the handoff CLI for task state; do not manually edit its persisted records or rely on chat history alone.
- Prefer `npm run workflow` for offline preflight, complete MCP PNG export saving/compression with automatic receipts, and actual design observation comparison. Read `tools/workflow/README.md`; do not write a new export/decode/validation script each round or manually transcribe Base64. The host forwards the complete tool return as data; this CLI has no MCP connection. Local-only preflight leaves remote scope unverified; consent failures cannot be ready. Due maintenance does not interrupt active production.
- Use `workflow snapshot` and `compare --allow` for trials and cross-session checks. Capture composition, corner radius, masks, image identity/crop and layer order before asserting them unchanged; missing observations prove nothing. Hashes and receipts establish recorded facts, not aesthetics, authenticity, rights or approval. Trial/preview labels do not claim formal handoff completion.
- Preserve the user's enjoyment of selecting images. Experimental suggestions are optional alternatives informed by cited examples/feedback; distinguish inferred preferences from confirmed preferences. Do not automatically choose the model's favorite.
- Read selected images and text from the user's authorized Figma/Pixso target region when available. Reuse saved targets; do not ask the user to repeat content the tools can read. A reference image is not a final selection, and presence in a design file is not license evidence.
- Before delegation and delivery, refresh the relevant source region and check the recorded revision. Only one executor may operate a shared design file or desktop surface at a time. A CLI claim is local coordination, not a lock on the design app.
- Discover actual tool capabilities before acting; no fabricated MCP results. The CLI accepts normalized snapshots but does not itself connect to Figma/Pixso. Model/session dispatch remains the host's responsibility and follows the user's explicit authorization.
- For Pixso production, read `docs/pixso-execution.md`: reuse the tool's documented copy operation, retain full exports in the host runtime, and transfer large results programmatically without model-written Base64 chunks. Save succeeds before decode, decode succeeds before batch compression; do not continue a dependent step after failure. Reuse concrete per-batch consent scope subsets instead of redefining the purpose at each step.
- Follow the user's current reference and latest feedback; a fixed template is optional. Preserve any properties the user asks to keep. Check that text is readable with no obvious omissions; do not add strict aesthetic gates or repeatedly refine accepted work. The model still directly uses the authorized Pixso tools for design work; the CLI handles mechanical facts and handoff.
- Use the user's own Figma account, connection, and file. Never hardcode or commit account IDs, file keys, node IDs, private URLs, credentials, or integration configuration.
- If Figma access is needed, guide the user to configure it inside their own AI client. Never ask them to paste a secret into the repository or chat.

## Private working data

- Keep backgrounds, source documents, workbooks, text, raw exports, finished exports, and temporary files under `.local/`.
- Do not commit actual content data, source images, generated daily signs, delivery ZIP files, credentials, or private Figma identifiers.
- Do not weaken `.gitignore` protections to make a local workflow easier.

## Delivery workflow

- Use the latest reference/feedback and keep normal progress narration brief; interrupt only for a real blocker or decision.
- Export explicitly selected daily-sign frames as original-size 1x PNG files into `.local/export-raw/` unless the user requests another scale.
- Save an explicit batch manifest with each rawPath/outputName and optional current reference, brief and Pixso target. Run `npm run workflow -- batch-export --input .local/batch.json --output .local/delivery/NEW-DIRECTORY`; resume via its report.json. Never scan all of export-raw or guess the newest version.
- Batch compression reuses the shared core and preserves dimensions; failure to meet the byte limit is reported without silently resizing or exporting at 2x. Existing compress CLI remains available with explicit files and `--no-resize`.
- Deliver the specified PNGs to the user; machine manifests and reports stay local. New sessions use the batch report as their local handoff entry and still refresh cloud observations before remote work.
- Validate every successful output is a readable PNG no larger than 204,800 bytes.
- The browser UI and CLI must continue to use the same compression core.

## Verification

After code changes, run `npm test` and `npm run build` from this repository root. Keep dependencies installed in this main workspace. When validating merged worktree changes, install dependencies and test inside the worktree containing the merged result; do not borrow another workspace's dependencies.
